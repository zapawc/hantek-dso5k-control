# HANTEK-DEV-01 — Acquisition protocol investigation

**Decision: keep remote SINGLE, EXT control, and paired live waveforms unavailable.** The first new hardware question is whether one explicitly approved CH1 display-buffer request produces a complete stream on the 2015 firmware without leaving an unsettled transfer. That test cannot establish a fresh acquisition. Its preconditions are in the [qualification plan](ISSUE_1_HARDWARE_PLAN.md).

## Baseline and scope

The published [immutable v0.1.0 preview](https://github.com/zapawc/hantek-dso5k-control/releases/tag/v0.1.0) resolves to 0cc1985288bafeb2ee932945937ea84be852e9f8. Its sanitized public history is distinct from local historical development and instrument evidence. The packaged CLI qualification was performed on the earlier local build. Sanitization changed the public settings vocabulary and schema, with the same transport and decoded bytes. Read-only settings and qualitative screen observation are the qualified live capabilities. Both graphics aggregates differed and two classified S92 events occurred in the packaged run. Four primary replies completed, 199 stable settings bytes agreed, and strict session integrity remained FAIL (exit 5). Current consumers pin the immutable release or commit and retain [schema 2.0 and exit-code semantics](../SETTINGS_V2.md).

## Findings

- **Readiness and completion.** S01 exposes a serialized display-facing state. Raw values 2 and 3 have been observed, but a value by itself cannot distinguish a new arm, ordinary wait, stale trigger indication, post-trigger capture, or completion of a uniquely identifiable shot. The vendor manual describes distinct front-panel indications for ready, post-trigger capture and finished SINGLE. Correlating those with timed settings reads is useful, but sparse USB snapshots can miss transitions. Polling more often has no qualification basis. See the [manufacturer manual](https://www.hantek.com/Product/5000P/DSO5000P_Manual.pdf).
- **Arm, disarm and trigger source.** S13 queues a key and responds with menu state. A valid S93 does not attest key consumption or the requested state transition. The candidate SINGLE key needs an independent readiness witness and an independently verified restoration path. RUN/STOP is a toggle, so a second keypress after an ambiguous result is unsafe. Settings disclose source and mode separately. EXT/5 and EXT labels from the [manufacturer specifications](https://www.hantek.com/products/detail/96) do not assign wire values, approve a connector voltage, or establish remote control. Candidate wire mappings remain community/static leads.
- **Waveforms.** S02 subtype 1 has separate CH1/CH2 paths. The multisource path loops through CH1, CH2 and the third internal source sequentially. It supplies no shared generation token, and the source byte echoed in data for a multisource request is the requested selector. A complete stream can be old. STOP/SINGLE retention, producer advance, callback effects, and source identification within multisource replies are blockers.
- **Sample interpretation.** The stream presents one signed display code per point, with a count on the wire. Scope settings provide candidate timebase, zoom, probe, gain, polarity and position context. The data do not carry ADC sampling interval, trigger index, record depth, acquisition timestamp or engineering units. The reported historical 3,200-point mode has no independently revalidated raw S02 transcript in this review. A verified historical 4,164-point CSV came from an explicit front-panel file save, and has no proven relationship to S02 or a particular trigger. Community reports describe a display window that changes with the menu, depth and timebase. They propose sample interval equal to visible span divided by point count and voltage conversion based on signed code minus vertical position. Verify the geometry, scaling, sign and probe convention against known inputs before using these formulas. [Community protocol](https://github.com/kooscode/hantek-dso5000p-linux/blob/b0facf139fb1b3da0a8c3ad0fa77a9eda76e1c46/protocol/PROTOCOL.md)
- **Completion lookalikes.** S92 is transfer-status-shaped and can arrive asynchronously. A particular frame's cause remains unresolved. S22 returns display-formatted cached measurements, and the observed CH1 frequency response was unavailable. Screens show render state and may retain old waveforms. A frequency counter can continue during a pause according to the vendor manual. Host or scope clock reads timestamp observations and cannot identify the acquisition.

## Offline work that reduces hardware scope

1. Complete the S02 producer-to-sender and resource-callback trace. Determine what advances the queue, when each channel is latched, whether a frozen pair is held, how to recognize a missing source, and whether calls can change state beyond the reviewed volatile transfer bookkeeping. Require call-path evidence before any new request.
2. Follow the SINGLE key through UI consumption, pretrigger readiness, event-driven completion and persistence. Find a conservative inverse for each action from a known starting state. Establish where the DISPLAY state may skip or conflate acquisition transitions and whether any read-only evidence captures a new generation.
3. Replay independently framed fixtures before enabling candidate code. Include split and coalesced records, unavailable with and without terminal, wrong echoed selector, zero and oversized counts, per-frame chunk overflow, missing terminal, mismatched count, stale primary before write, late/duplicate/early S92, unknown opcode and truncated trailing data. Multisource fixtures must reject channel ambiguity, including a missing middle source with no trustworthy marker. Exercise coherent, mismatched, stale and uncorrelated metadata using distinct synthetic event labels. Fixtures can test rejection logic but cannot prove the device lifecycle.
4. Use an independent stimulus/record witness to qualify voltage and timing interpretation, freshness, and common event identity. Keep conversion derived or null until defaults and units are measured.
