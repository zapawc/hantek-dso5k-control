# HANTEK-DEV-01 — Prospective CLI and acquisition metadata

Keep all v0.1.0 commands, exit codes and settings/capture schema 2.0 stable. The current read-only qualification can establish framing and stable settings; exit 5 can indicate that primary replies completed while strict session integrity failed. A consumer should read the manifest alongside the exit code. See [current CLI contract](../CLI_CONTRACT.md).

After hardware qualification, consider a separate capture single subcommand with explicit channels, trigger source, trigger wait budget and output directory. It should reject unsupported firmware, acquisition modes, electrical configurations and channel combinations before hardware contact and avoid silently substituting another trigger mode. Trigger wait, transfer windows and total run deadlines are independent. Until a safely observable arm and inverse exist, keep instrument configuration manual and describe any resulting capability as observation-only. The spelling is a proposal and no package implements it.

| Proposed manifest field group | Data to record |
| --- | --- |
| Envelope | Acquisition-specific schema version 1.0 under a new file/schema identifier, operation, host run UUID, instrument/model/firmware evidence, immutable package pin, plan ID, requested channels and settings context. A host UUID identifies an attempt only. |
| Readiness and trigger | Requested vs observed source, mode, coupling, edge, threshold and their evidence. Arm/trigger/completion observations with raw state, provenance, host monotonic time, optional host UTC and uncertainty. Device event or generation ID is nullable and can be shared only if verified. |
| Channel records | Channel/source attribution, requested/observed points and bytes, signed encoding, scale, offset, probe factor, viewport and derived or measured sample interval. Record origin for units and calibration. Store actual capture encoding and derivation mode, not a guessed ADC period. Trigger index, trigger-relative origin and acquisition time are nullable. |
| Integrity | Separate transport, frame, availability, freshness, pair coherence, configuration and restoration statuses using pass/fail/inconclusive/not-tested and machine-readable reasons. Status events retain origin uncertainty. Attach timing, checksums, digests and paths to preserved artifacts. |
| Failures | Record terminal stage, failure reason, channels present, expected/received counts, final observed instrument state, pending-command marker, and whether manual recovery remains required. Null means absent or unproven; do not substitute zero time or report a usable pair. |

Examples of stage outcomes include ownership blocked, readiness unproven, trigger wait deadline reached, waveform unavailable, waveform incomplete, waveform attribution ambiguous, pair coherence unproven, and restoration unverified. A wait deadline describes host observation; the instrument may still be armed. Reserve exit mappings for a reviewed future command and avoid redefining exit 5 for existing consumers. Keep new evidence dimensions separate from the application's own acceptance thresholds, analysis and presentation. Consumers pin an approved wheel or immutable commit and deliberately migrate. See [integration ADR](../adr/0001-cross-project-integration.md).
