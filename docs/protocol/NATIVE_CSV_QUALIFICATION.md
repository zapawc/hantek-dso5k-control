# Supervised S10 qualification — planned protocol and observed results

**Historical protocol:** The steps below describe the bounded qualification design and its fail-closed requirements. DEV-06A qualified one supervised predecessor transfer, and the packaged DEV-07 CLI subsequently passed a separately authorized live test on 2026-11-20 UTC. This record does not authorize additional device operations. Offline replay never opens USB.

1. Start with original 2015 firmware, a responsive instrument and a closed, disposable, previously exported CH1 CSV at the root of the currently mounted writable front FAT32 drive. Establish exact filename, provenance and presence through current operator evidence. Nothing should be exporting or writing. Record the visible frozen state if available and require it if claiming preservation. Have the verified reference size and SHA-256 on Windows and an absent destination on a supported local filesystem. A Windows copy does not establish instrument-side presence. If the known file is missing, its presence is uncertain or a separate export is needed, stop.
2. Confirm operator-declared single client, check concrete client/assignment conflicts and settled command history, retain the cooperative lease and interruption marker, and verify the unique known DSO5102P. Use only WinUSB interface 0 on VID 049F:505A, bulk IN `0x81` and OUT `0x02`. Claim once. Record 12 continuous seconds of receive-only silence. Any byte (including S92), error, ambiguous device or unresolved history blocks the request.
3. The only proposed write is S10 for the explicitly reviewed filename, once, after at least 550 ms from any prior command. For synthetic basename `WaveData1.csv`, the exact frame is `53 1B 00 10 00 2F 6D 6E 74 2F 75 64 69 73 6B 2F 57 61 76 65 44 61 74 61 31 2E 63 73 76 32`. Bind the actual preauthorized frame to the operator-approved reference before opening. No echo, settings, listing, S02, or extra S10.
4. Capture the full 12-second response window after write completion. Log raw TX/RX, original transfer boundaries, timestamps, parser outcomes and cleanup. Cap file bytes at 98,304, raw RX at 102,400, and enforce the exact frame count from the verified reference size. Expect ordered S90 subtype-01 data frames and one subtype-02 terminal. Accept only expected chunk sizes, exact byte count, valid individual checksums, terminal sum and reference SHA-256. Continue receive-only after a valid terminal to detect trailing traffic. In the earlier conservative pilot plan, S92 was treated as blocking. The later reviewed DEV-07 CLI instead recognizes the exact checksum-valid S92 shape at frame boundaries and records it separately; unknown or duplicate frames, partial data, timeouts, checksum errors, disconnects and unexpected operator-observed behavior remain blocking. No S92 occurred in the packaged live run.
5. On a block/failure, cease writes immediately, retain all evidence and exclusive resources until cleanup, and release interface and lease. Preserve the interruption marker if completion is ambiguous. Treat a disconnect or a possibly in-flight firmware sender as unresolved. No flush, retries, endpoint reset, power cycle, drive removal or recovery command. If there is an instrument symptom, record it and obtain operator review before any further action.
6. Publish a local output only after all gates succeed, without replacement. Rehash the output and compare to the independent reference. Record the post-test panel state by observation only. Label panel retention as observed or unknown independently of byte integrity. File identity verifies the staged artifact carried over USB. The pilot cannot establish pair coherence, trigger correctness or sample freshness.

S10 uses `r+b` even though the traced sender does not explicitly write file contents. Possible effects include mount metadata/access time, USB/UI status bookkeeping, and an unclean or stalled transfer under storage/USB faults. No new export or internal storage access is needed for this pilot.

- **Qualification boundary:** only this packaged CLI's single, closed **CH1** staged-file retrieval on the observed device and conditions is hardware-qualified. The packaged S92 classification remains **offline tested** (a status frame occurred in the predecessor DEV-06A run, but not in this DEV-07 live run). No additional USB tests are needed merely to repeat this milestone.

The observed success does not change the fail-closed preflight, one-request limit or the requirement for separate approval of any new hardware operation.
